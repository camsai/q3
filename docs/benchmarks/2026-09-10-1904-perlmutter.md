# Benchmarking Q3 on NERSC Perlmutter — protocol

A plan, not results. Written 2026-09-10 after a first pass of ad-hoc measurement
whose main product was a list of ways to get this wrong.

Two companion documents already exist and this does not replace either:

-   [`docs/q3_vs_qe_benchmark_plan.md`](../../docs/q3_vs_qe_benchmark_plan.md) — the
    comparison against Quantum ESPRESSO. That is a different question (how does Q3 compare
    to another code) from this one (how should Q3 be run here, and did a commit make it
    slower). Its system ladder and its two measurement traps apply to both.
-   [`docs/performance_nersc_perlmutter.md`](../../docs/performance_nersc_perlmutter.md) —
    the numbers measured so far, all single-shot and none with an error bar.

And a harness exists:
[`scripts/validation/run_mpi_reproducibility_matrix.py`](../../scripts/validation/run_mpi_reproducibility_matrix.py)
already sweeps topologies, repeats each three times, records `wall_seconds` beside every
energy component, and captures the git commit and binary digest. **Extend it. Do not
write a second one.** The ad-hoc `scripts/hpc/nersc_perlmutter/benchmark.sh` was written before
that was noticed; it should either fold into the matrix runner or stay explicitly as the
quick-look tool it is.

## Goals

Two, and they want different treatment:

| Goal                   | Question                        | Needs                                              |
| ---------------------- | ------------------------------- | -------------------------------------------------- |
| Configuration guidance | what should I set for this job? | breadth; tolerates noise                           |
| Regression detection   | did commit X make it slower?    | tight variance control, stored baselines, no sweep |

Capability claims ("Q3 scales to N ranks") and allocation planning are out of scope here:
the first needs weak scaling and multi-node evidence this plan only starts to gather, and
the second needs real production inputs rather than examples.

## Measurement substrate

**Timings come from the program.** `results.json` now carries a `timings_ms` block —
per-stage Davidson breakdown, `total`, `fft_calls`, `davidson_iterations`,
`hamiltonian_applications` — beside the `execution` topology and `provenance` that were
already there. Before this, every per-stage number had to be regular-expressioned out of
console text, which fails silently: a crashed run has no timing block to match and the
scraper reports a blank rather than a failure.

Two caveats that belong beside any use of those numbers:

-   The four `hamiltonian_*` sub-timers are **not a partition** of
    `hamiltonian_application`. A 2-atom silicon run reports 72.9 ms of `hamiltonian_fft`
    against 52.2 ms of `hamiltonian_application`, because the sub-timers live in the
    applicator and the parent is accumulated around the call site in `davidson.hpp`. Compare
    them across configurations; do not decompose the parent with them.
-   `total` is the sum the log prints as `TOTAL`, which excludes the sub-components for the
    same reason.

## Controls

Each of these was learned by getting it wrong.

| Control                                   | Why                                                                     |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `use_deterministic_fft_planning`          | `FFTW_MEASURE` picks a different plan per run; timings stop reproducing |
| `--exclusive` allocations                 | a shared node contaminates                                              |
| Record the node ID                        | runs landed on `nid004144`, `nid004151`, `nid004164`, `nid004201/3/4`   |
| Pin module versions and the commit SHA    | CPE upgrades move the numbers                                           |
| Set `OMP_NUM_THREADS` explicitly          | the container images set it to 1; nothing should be assumed             |
| **Do not** set affinity unless testing it | `--cpu-bind=cores` measured 45% SLOWER than leaving the scheduler alone |
| Flag the replicated-G fallback            | a fallback run is measuring different work, not slower work             |
| Flag which intra-pool split was used      | reciprocal space and `--distribute-bands` are different modes           |
| Solver time as headline, wall as second   | `srun` startup is 2–9 s and swamps sub-minute runs                      |

## Statistics

-   **5 repeats**, discard the first, report **median and min–max**. The first repetition
    is not like the others: measured at 182 ms against a 137 ms median for serial silicon,
    and 341 ms against 122 ms for two ranks — nearly 3×.
-   **The noise floor is measured, and it depends on run length** (2026-09-10, 9–10 kept
    repetitions each):

    | deck            | topology              | median   | relative sd |
    | --------------- | --------------------- | -------- | ----------- |
    | silicon, 137 ms | serial                | 137.0 ms | 1.5%        |
    | silicon         | `mpi_4_ranks_2_pools` | 45.3 ms  | 10.7%       |
    | copper, 39 s    | serial                | 39017 ms | 5.0%        |
    | copper          | `mpi_4_ranks`         | 35490 ms | 0.4%        |
    | copper          | `mpi_4_ranks_bands`   | 15367 ms | 0.3%        |

    A short run is an order of magnitude noisier in relative terms than a long one, so a
    single fixed threshold is wrong in one direction or the other.
    `scripts/hpc/nersc_perlmutter/compare_benchmark.py` therefore takes the threshold **per entry**
    from that entry's own spread — three relative standard deviations, with a 5% floor.

-   **What this retrospectively invalidates.** Against a ~11% floor on the small deck, the
    earlier "ScaLAPACK is 24% slower" is about 2σ and not safely distinguishable from the
    machine; it is marked as marginal rather than dropped. These clear it comfortably: pool
    scaling 28.9×, OpenMP 8 vs 32 threads (46%), thread binding (45%), GPU against 32
    threads (37%), reciprocal-space band groups against serial on copper (42%).
-   **Energy is a gate, not a metric.** A run whose energy moves is excluded from the
    timing statistics, not averaged into them.

## System ladder

All four decks exist; none needs to be authored.

| Tier   | Deck                                                    | Shape                                            | Exercises                          |
| ------ | ------------------------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| Small  | `total_energy--semiconductor--silicon/nc_kpt_8x8x8.yml` | 2 atoms, 60 irreducible k-points                 | pool scaling; CI-able in seconds   |
| Medium | `total_energy--metal--copper/nc_3x3x3_bench.yml`        | 27 atoms, 280 bands, Γ-only, `max_iterations: 3` | threading, intra-pool splits, GPU  |
| Large  | `total_energy--semiconductor--silicon/nc_6x6x6.yml`     | 432 atoms, 1040 bands, Γ-only, ~167k plane waves | band distribution, multi-node, GPU |
| Wide-k | `total_energy--semimetal--graphite/nc_d3.yml`           | 4 atoms, 12×12×6 k-grid                          | pool scaling past one node         |

The large deck carries its own note: _"~45 GB per rank with the basis replicated, so it
does not run in CI or on a laptop."_ That is the point of it — it does not fit in a 40 GB
A100 replicated, and a 512 GB CPU node holds about eleven replicated ranks, so it forces
the distribution axes to be used rather than merely offered.

Both Γ-only decks need capped-iteration variants for timing (the Cu bench deck already has
one). A capped run does **not** converge, so its energy is only comparable against the same
deck's own value, never against the converged reference.

## Axes

-   Threads: 1, 2, 4, 8, 16, 32, 64 (the optimum measured so far is 8, and 64 is slower than 4)
-   Ranks: 1 … node size, then multi-node
-   Pools vs. intra-pool split, and **which** split: reciprocal space (default) or
    `--distribute-bands`
-   ScaLAPACK on/off
-   GPU: `--precision double` and `mixed`; **one device only** — `q3_gpu_cuda` has no
    MPI, so "one per rank" means independent duplicate runs, and multi-GPU strong scaling
    is a feature to implement rather than a measurement to take. Throughput across devices
    is measurable and is linear to sixteen.

Only meaningful cells: a Γ-only deck cannot use pools; pools cannot exceed the irreducible
k-point count; the reciprocal-space split fell back to replicated G-vectors above four
ranks per pool on both decks measured.

**`--distribute-bands` was the least-explored axis and turned out to be the one that
works.** Measured 2026-09-10, four ranks, four repetitions with the first discarded:

| deck                    | serial   | reciprocal space | `--distribute-bands` | pools           |
| ----------------------- | -------- | ---------------- | -------------------- | --------------- |
| Copper 3×3×3, Γ-only    | 38387 ms | 35338 (1.09×)    | **15354 (2.50×)**    | n/a             |
| Silicon 8×8×8, 60 k-pts | 3520 ms  | 3243 (1.09×)     | 1896 (1.86×)         | **659 (5.34×)** |

Spreads of 0.2–0.6% on the MPI rows, so both results are far outside the noise. The
earlier conclusion that band groups cost more than they return described the **default
reciprocal-space split only**; the mode Q3 provides for the Γ-only case had never been
measured.

Note that the subspace solve takes the serial path under band distribution, because
`enable_band_distribution()` sets `group_size()` to 1 — correct, but it means ScaLAPACK
contributes nothing in that mode today. Given that band distribution is 2.5× while
ScaLAPACK measured no difference at all, that is not currently a loss worth chasing.

Still unmeasured: `nc_6x6x6.yml`, the 432-atom deck this mode was written for, and every
multi-node topology.

## Multi-node — done, and it costs nothing

Measured on graphite (864 → **76** irreducible k-points). At matched rank counts the
two-node runs are not slower: 840.5 ms against 840.9 ms at eight ranks, 428.9 against
459.9 at sixteen. All twenty runs agree to 1.4e-14 Ry, and each topology is bit-identical
across its own repetitions. Details in
[`docs/performance_nersc_perlmutter.md`](../../docs/performance_nersc_perlmutter.md).

One limitation of the harness to keep in view: `allocation_node_names` records the
**allocation's** nodes, not the step's, so every topology in one allocation reports the
same value. It is provenance, not proof that a topology spanned nodes — Q3's log carries
rank and pool counts but no hostnames. Establishing placement needs either a separate
`srun hostname` or a per-rank hostname in the log.

## Output and storage

One JSON per run — configuration, `timings_ms`, energy, `execution`, `provenance`, node ID
— aggregated into a committed results file keyed by commit SHA, under `docs/benchmarks/`
beside this document. That makes "did this get slower" a diff rather than an excavation.

## Order of work

1. `timings_ms` in `results.json` — **done**, this is what makes the rest measurable.
2. Extend `run_mpi_reproducibility_matrix.py`: read `timings_ms`, add multi-node, add the
   `--distribute-bands` axis, record node ID and the fallback/split flags — **done**,
   along with the four ladder decks as opt-in cases.
3. Measure run-to-run spread on one deck to fix a significance threshold — **done**, on
   two decks, because one was not enough: the floor turned out to depend on run length.
4. Run the ladder — **small, medium, wide-k and multi-node done**. The large deck
   (`nc_6x6x6`) is characterised but **not measurable as it stands**: 38.9 GB per rank,
   which caps a node at about twelve ranks and puts it out of reach of a 40 GB A100; and
   four band-distributed ranks failed to finish three SCF iterations in 83 minutes, so a
   single point costs over 5.5 node-hours and its real cost is still unknown. Sweeping it
   needs either several nodes or a deliberately cheaper variant of the deck, and either is
   a decision about how much machine time one number is worth.
5. Commit baselines under `docs/benchmarks/`, and compare with
   `scripts/hpc/nersc_perlmutter/compare_benchmark.py --baseline`.

**Correction to this step as first written.** It said to wire a reduced set into
`.github/workflows/scheduled_tests.yml`. That cannot work: the workflow runs on
`ubuntu-latest`, which has no route to Perlmutter and no Slurm. A GitHub runner can only
regression-test itself, which measures the runner rather than this machine.

The mechanism that does fit is NERSC's `scrontab` — a Slurm-scheduled recurring job that
runs the matrix, writes a summary, and compares it against the committed baseline. That is
a recurring job on a shared allocation, so it wants a deliberate decision rather than being
set up in passing. Until then the loop is manual: run the matrix, run `compare_benchmark.py
--baseline`, commit the new baseline when a change is intended.
